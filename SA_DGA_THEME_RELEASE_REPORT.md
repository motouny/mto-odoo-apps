9d. **CRITICAL FIX (v1.2): the custom font was never actually rendering.** `views/layout_templates.xml` injected `--dga-font-arabic`/`--dga-font-latin` into a `<style>` tag using `t-esc`. Those values deliberately contain literal `"` characters (CSS font-family syntax, e.g. `"IBM Plex Sans Arabic"`); `t-esc` HTML-escapes quotes to `&#34;`, which is invalid CSS - the whole custom-property declaration silently failed and **every single page, backend and frontend, fell back to the browser's default serif font (Times)** since the runtime font override was first built in v1.0/v1.1. This was found only because the user sent a real screenshot and asked why the font "looked plain" - `getComputedStyle` confirmed the broken `&#34;IBM Plex Sans&#34;...` token stream. Fixed with `t-out` + `markupsafe.Markup()` (the modern, non-deprecated equivalent of `t-raw`, wrapped in `_sa_dga_font_pair_values()` in `models/res_company.py` since these are trusted constants, not user input). **Every prior claim or screenshot about the Arabic/Latin font pairing predates this fix** and was likely showing the browser default, not the intended font - re-verify anything font-related that was checked before this was fixed.
9e. **Real DGA homepage template** (v1.2, `sa_dga_theme_website`): `website.homepage` ships genuinely empty in Odoo core (confirmed: `<div id="wrap" class="oe_structure oe_empty"/>`, not a bug on our side) - there was no real homepage content at all before this. `views/website_homepage_dga.xml` inherits it and adds four real, fully snippet-editable sections, **active by default** (unlike the header/footer, there's no existing "homepage variant picker" to slot into, and a blank homepage was the actual complaint being fixed): a hero (reusing `s_banner`'s structural classes), a quick e-services grid (reusing `s_features`'s 3-column pattern), an animated stats/counters section, and a news/announcements section. The news section is static demo content, not wired to `website_blog` (not a dependency of this module - a documented follow-up if real dynamic news is wanted).

Once Arabic is available, the language selector **automatically appears** in the header - it was already built into the inherited Default header template (`t-if="len(frontend_languages) > 1"`), so no extra header code was needed for this.

9i. **Brand identity extended to Odoo's own built-in UI** (v1.5, user pointed out a screenshot where the active "sections menu" tab - e.g. Configuration/Tags/Assets under an app - was still Odoo's own default purple, not the theme's): researched two ways to fix this - (a) hook `web._assets_primary_variables` and override Odoo's `$o-brand-primary`/`$o-action` Sass variables at compile time (the same mechanism `web_enterprise` itself uses for its own brand purple), or (b) extend the existing runtime CSS-custom-property system. **Deliberately chose (b)**: hijacking the Sass variables would bake the color into the compiled CSS bundle at build time, breaking the explicit requirement that colors stay "changeable from Settings" - Bootstrap's own Sass color functions (`darken()`, `mix()`) can't operate on a `var()` reference either, so there's no way to make the Sass-level override itself dynamic. Instead, confirmed (by reading `web/static/src/webclient/navbar/navbar.scss` directly) that Odoo's own NavBar already exposes `--NavBar-entry-backgroundColor--active` etc. as CSS custom properties in *core* `web` (consumed via `var(..., $sass-fallback)`), not just in Enterprise - overriding them in `backend.scss` on `.o_main_navbar` re-themes the active section tab with zero Sass changes, staying fully dynamic. Extended the same reasoning to a handful of standard Bootstrap components Odoo hard-codes to its own brand color at compile time (no existing custom-property hook, so these are direct `var(--dga-primary)` overrides): checked checkbox/radio background, input/select focus border+glow, notebook active-tab accent, `.list-group-item`/`.nav-pills` active states. Also added `--dga-primary-rgb`/`--dga-accent-rgb` (R,G,B triplets, computed server-side in `_sa_dga_rgb_triplet()`) so `rgba()`-based glows (focus rings) can be built from the runtime color too, and made `--dga-focus-ring` itself dynamic (previously a static compile-time value that didn't track the Settings color picker). Verified live via `getComputedStyle`: `--NavBar-entry-backgroundColor--active` and a synthetic checked-checkbox's background both compute to the runtime primary color (`#5e4766`).

16. **Real bugs found and fixed during this build** (all confirmed via actual browser testing, not assumed):
    - **Category trap**: the module was initially categorized `'Theme'`. Odoo's `website` module treats that category (and its children) as a mutually-exclusive, explicitly-selected page theme and **silently excludes such modules' assets from every website-scoped bundle** unless picked as `website.theme_id` - our entire SCSS/JS payload was being dropped from the compiled bundle with no error. Fixed by using category `'Website'` instead.
    - **Google Fonts URL syntax**: the CSS2 API's semicolon-separated multi-weight syntax (`wght@400;500;600;700`) inside an `@import url(...)` corrupted the *entire* compiled CSS bundle - Odoo's asset minifier splits/reorders `@import` statements on `;` without respecting the quoted-string context, dropping the whole stylesheet to ~2 parsed rules. Fixed by switching to the legacy comma-separated Google Fonts API (matches Odoo core's own `$o-theme-font-configs` convention).
    - **Sass `min()`/`max()` vs. native CSS**: `min(92vw, 640px)` in the app-launcher SCSS was evaluated by Sass itself (mismatched units), throwing `Incompatible units: 'px' and 'vw'` and breaking the *entire* `web.assets_web` bundle compile. Fixed via whole-expression string interpolation (`#{"min(92vw, 640px)"}`) so Sass emits it as literal CSS text.
    - **`<input>` value-attribute quirk**: the custom color-picker widget's `t-att-value` only seeds the DOM's initial value; further updates after first mount don't visually re-sync (same well-known behavior as in React) - unlike the radio widget's `t-att-checked`, which does re-sync. Fixed with `t-key` forcing a remount on value change.
    - **Related-field onchange unreliability**: a server-side `@api.onchange` on a `related=` Selection field edited via a custom widget on `res.config.settings` did not reliably fire over RPC in testing. Reworked the preset -> color sync to be fully client-side (`DgaPresetRadioField`), which is also a better match for the "applied instantly" UI copy.
    - Two cross-process asset/session caching traps encountered purely as *environment* issues (not module bugs): editing files while a separate `odoo-bin shell` process writes to the same DB doesn't reliably invalidate the running HTTP server's in-memory caches - fixed each time by a full server restart rather than assuming a live-reload.
    - **(v1.1) `body.o_web_client` selector bug**: the sidebar's layout-shift CSS was written as `body.o_dga_sidebar_collapsed .o_web_client { ... }` (descendant combinator), but `.o_web_client` IS `<body>` itself (set server-side in `web/views/webclient_templates.xml`), not an ancestor-descendant relationship - the selector matched nothing. Fixed to a compound selector: `body.o_web_client.o_dga_sidebar_collapsed`.
    - **(v1.1) Stale xpath after upstream `position="replace"`**: the DGA header variant originally targeted `//header//nav position="before"`, inheriting `website.template_header_default` - but that parent view's own xpath *replaces* the literal `<nav>` with a `<t t-call="website.navbar">` wrapper, so the tag no longer exists in the combined arch for a second inheriting view to locate. Activating the view raised `Element '<xpath expr="//header//nav">' cannot be located in parent view`. Fixed by targeting `//header/*[1] position="before"` instead - robust regardless of what the header's first child actually is.
    - **(v1.1) Browser HTTP-cache false negatives during testing**: repeatedly appeared to have a broken/unmirrored RTL layout, traced to the test browser tab reusing a cached `web.assets_web.min.js`/`.css` URL from before Arabic was configured, rather than the (correctly-generated) `.rtl.min.css` bundle - confirmed via a fresh `curl` session bypassing all browser cache. Not a module bug; worth remembering that a fingerprinted-URL browser cache can outlast even a full server restart from the tester's point of view.
    - **(v1.1, real & serious) `t-esc` corrupting the runtime font override**: `views/layout_templates.xml` injects `--dga-font-arabic`/`--dga-font-latin` into a `<style>` block using `t-esc` on values that deliberately contain literal double quotes (e.g. `"IBM Plex Sans Arabic"`, required CSS font-family syntax for multi-word names). `t-esc` HTML-escapes those quotes to `&#34;`, which isn't valid CSS - the entire custom-property declaration silently became invalid and every page fell back to the browser's default serif font (Times), on **both backend and frontend**, since this whole time. Confirmed via `getComputedStyle` showing the literal broken `&#34;IBM Plex Sans&#34;...` token stream as the property's raw value. This means the custom Arabic/Latin font pairing (the app's own headline feature) has never actually rendered correctly since it was implemented, despite colors working fine (hex colors have no quotes, so they were never affected - this is why testing "looked fine" up to now). Fixed by switching those two lines to `t-raw` (the font-pair values are trusted constants from `DGA_FONT_PAIRS`, not user input, so unescaped output is safe). **Re-verify all previous screenshots/claims about the font pairing** - they predate this fix and may have been showing the browser default font, not the intended one.
